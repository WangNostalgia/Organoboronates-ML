# TorchSISSO symbolic-regression baseline

This branch adds a **standalone TorchSISSO baseline** for the organoboronate
activation-energy dataset. It intentionally does **not** modify `main.py` or the
default model registry, because TorchSISSO is a symbolic-regression package with
a different API from scikit-learn estimators.

The script follows the same high-level evaluation rule documented in the main
README:

- create one shared 80/20 development/final-test split;
- use `random_state=40` for that split;
- perform model selection only inside the development set;
- score the final test set once after the TorchSISSO grid is chosen.

## Added files

```text
requirements-torchsisso.txt
example/train_torchsisso.py
docs/torchsisso.md
```

## Installation

Use a fresh environment. Do not install this into an already messy SISSO++ build
environment.

### CPU-first installation

```bash
conda create -n organoboronates-torchsisso python=3.10 -y
conda activate organoboronates-torchsisso

python -m pip install -U pip setuptools wheel
python -m pip install -r requirements-torchsisso.txt
```

Then verify the package import:

```bash
python -c "from TorchSisso import SissoModel; import torch; print('TorchSISSO OK', torch.__version__, torch.cuda.is_available())"
```

The PyPI package/import name is case-sensitive in practice:

```python
from TorchSisso import SissoModel
```

### GPU installation

First make sure the machine sees an NVIDIA GPU:

```bash
nvidia-smi
```

Then install the CUDA-enabled PyTorch wheel generated by the official PyTorch
installer page for your platform. After that, install the rest:

```bash
python -m pip install -r requirements-torchsisso.txt
```

If `torch.cuda.is_available()` is still `False`, run the script with CPU first
and debug CUDA separately.

## Quick smoke test

This skips CV and only checks that TorchSISSO can fit and produce final-test
outputs:

```bash
python example/train_torchsisso.py \
  --data example/B_dataset.csv \
  --target activation_energy \
  --output_dir models/TorchSISSO_smoke \
  --no_cv \
  --n_expansion 1 \
  --n_term 1 \
  --k 20 \
  --operators + - "*" / "pow(2)" ln
```

## Recommended first real run

This is conservative and should be the first real comparison run:

```bash
python example/train_torchsisso.py \
  --data example/B_dataset.csv \
  --target activation_energy \
  --output_dir models/TorchSISSO \
  --n_expansion 1 2 \
  --n_term 1 2 \
  --k 20 50 \
  --operators + - "*" / "pow(2)" ln \
  --initial_screening spearman 0.95
```

For a more exhaustive run, add `--n_term 3` and `--k 100`, but only after the
smaller grid works.

## Outputs

Each run writes timestamped artifacts under the output directory:

```text
models/TorchSISSO/
├── torchsisso_<timestamp>_metrics.json
├── torchsisso_<timestamp>_equation.txt
├── torchsisso_<timestamp>_predictions.csv
├── torchsisso_<timestamp>_fitted_metadata.joblib
├── torchsisso_<timestamp>_cv_results.csv
└── torchsisso_<timestamp>_cv_results_full.json
```

The most important fields in `*_metrics.json` are:

- `best_params`: selected TorchSISSO settings;
- `equation`: returned symbolic expression;
- `metrics.development`: score after refitting on the full development set;
- `metrics.final_test`: one-time final-test score;
- `feature_name_mapping`: mapping from sanitized feature names back to original
  CSV column names.

## Important interpretation note

The saved equation is fitted on **median-imputed and standardized descriptors**.
That means the formula is not directly in raw physical units. The saved
`*_fitted_metadata.joblib` contains the preprocessing pipeline and feature-name
mapping needed to reconstruct the actual input representation.

This is deliberate: it keeps TorchSISSO numerically stable and avoids fitting
with train/test leakage. Fold-local preprocessors are used during development CV,
and the final preprocessor is fit only on the development set before the one-time
final-test score.

## Why this is separate from `main.py`

The main pipeline assumes scikit-learn-style estimators and SHAP-RFECV feature
elimination. TorchSISSO performs its own symbolic feature construction and sparse
selection, so forcing it into the default registry would mix two different model
selection systems.

Keeping it standalone makes the comparison cleaner:

- same raw dataset;
- same fixed development/final-test boundary;
- development-only hyperparameter choice;
- separate symbolic equation artifacts.

## Suggested reporting language

When reporting these results, describe them as:

> A standalone TorchSISSO symbolic-regression baseline was evaluated using the
> same fixed 80/20 development/final-test split as the default ML pipeline.
> TorchSISSO hyperparameters were selected by repeated K-fold evaluation inside
> the development set only, and the final test set was scored once after the
> symbolic equation was locked.

This avoids overclaiming that TorchSISSO is part of the SHAP-RFECV/Optuna
registry.
